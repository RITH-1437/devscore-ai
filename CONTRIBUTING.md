# Contributing to GitRadar

Thanks for helping improve GitRadar. This guide covers local setup, development workflow, and how to submit changes.

For deeper technical docs, see the [`docs/`](docs/) directory.

## Before you start

- Read the [Code of Conduct](CODE_OF_CONDUCT.md)
- Check existing [issues](https://github.com/RITH-1437/devscore-ai/issues) to avoid duplicate work
- For bugs, use the bug report template; for features, use the feature request template

## Fork and clone

```bash
git clone https://github.com/<your-username>/devscore-ai.git
cd devscore-ai
git remote add upstream https://github.com/RITH-1437/devscore-ai.git
```

## Requirements

| Tool | Version |
|------|---------|
| PHP | 8.3+ |
| Composer | 2.x |
| Node.js | 18+ |
| npm | 9+ |
| MySQL / MariaDB | 8.0+ / 10.x (SQLite works for tests) |
| GitHub OAuth app | For login during development |
| AI API key | Gemini (recommended) or OpenRouter |

Optional: Redis for faster cache/queue — not required locally.

## Local setup

### Quick start

```bash
composer setup
```

This installs PHP dependencies, creates `.env` from `.env.example`, generates `APP_KEY`, runs migrations, and builds frontend assets.

### Manual setup

```bash
composer install
npm install
cp .env.example .env
php artisan key:generate
php artisan migrate
npm run build
```

### Environment configuration

Copy `.env.example` to `.env` and fill in placeholders. Never commit `.env`.

Minimum variables for local development:

```env
APP_KEY=                        # generated by php artisan key:generate
GITHUB_CLIENT_ID=your_github_client_id
GITHUB_CLIENT_SECRET=your_github_client_secret
GITHUB_REDIRECT_URI=http://localhost:8000/auth/github/callback

# At least one AI provider:
GEMINI_API_KEY=                 # preferred
OPENROUTER_API_KEY=             # fallback when GEMINI_API_KEY is empty

QUEUE_CONNECTION=database
DB_QUEUE_RETRY_AFTER=330
```

See [docs/environment.md](docs/environment.md) for the full reference.

### Database setup

Create a MySQL database:

```sql
CREATE DATABASE devscore_ai CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

Configure `.env`:

```env
DB_CONNECTION=mysql
DB_HOST=127.0.0.1
DB_PORT=3306
DB_DATABASE=devscore_ai
DB_USERNAME=root
DB_PASSWORD=
```

Run migrations:

```bash
php artisan migrate
```

### GitHub OAuth setup

Create an OAuth app at https://github.com/settings/developers:

| Field | Local value |
|-------|-------------|
| Homepage URL | `http://localhost:8000` |
| Authorization callback URL | `http://localhost:8000/auth/github/callback` |

Use your own client ID and secret in `.env`. Do not use production credentials.

See [docs/authentication.md](docs/authentication.md) for details.

## Running locally

All-in-one development (server + queue worker + Vite):

```bash
composer dev
```

Or run processes separately:

```bash
php artisan serve
php artisan queue:listen --tries=1 --timeout=0
npm run dev
```

Open http://localhost:8000 and sign in with GitHub. Repository sync and AI analysis require the queue worker.

## Testing

```bash
composer test
```

This clears config cache and runs PHPUnit. Add or update tests for behavior changes. Use `Http::fake()` for external API calls.

See [docs/testing.md](docs/testing.md) for test layout and conventions.

## Branch and commit workflow

1. Sync with upstream: `git fetch upstream && git checkout main && git merge upstream/main`
2. Create a branch: `git checkout -b fix/short-description`
3. Make focused changes — one concern per PR
4. Write commit messages that explain **why**, not just what changed
5. Run tests before pushing: `composer test`

## Pull request process

1. Push your branch to your fork
2. Open a PR against `main` on the upstream repository
3. Fill in the PR template completely
4. Ensure CI passes (tests workflow)
5. Update documentation in `docs/` when behavior or setup changes
6. Respond to review feedback

Do not commit:

- `.env` or secrets
- `vendor/`, `node_modules/`, or build artifacts
- Unrelated refactors mixed into feature work

## Code standards

- PHP 8.3+ with `declare(strict_types=1);` on new PHP files
- Follow existing Laravel conventions in `app/`
- Match surrounding naming, types, and documentation style
- Minimize scope — focused diffs are easier to review
- Document actual behavior only — no speculative features

## Reporting bugs

Use the [bug report template](.github/ISSUE_TEMPLATE/bug_report.yml). Include steps to reproduce, expected vs actual behavior, and your environment.

## Requesting features

Use the [feature request template](.github/ISSUE_TEMPLATE/feature_request.yml). Describe the problem, proposed solution, and use case.

## Security issues

Do not report vulnerabilities in public issues. See [SECURITY.md](SECURITY.md).

## Areas welcome for contribution

- UI/UX improvements (Blade, Tailwind, Alpine.js)
- Test coverage
- Documentation accuracy
- Error message clarity
- Performance (query efficiency, caching)

## Out of scope (unless discussed first)

- Additional AI providers beyond Gemini and OpenRouter
- Public REST API
- Features not reflected in the existing codebase
